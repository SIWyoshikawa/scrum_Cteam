# 学内施設・備品予約貸出管理システム 要望整理・初回提案書

> 本書は「学内施設・備品予約貸出管理システム 要望書」とチーム内対話を基にした初回提案である。画面項目、DB項目、細かな運用ルールは未確定であり、CAND番号は検討中の要件候補を示す仮IDである。正式なREQ IDではない。

## 1. システム概要

学内の施設、教室、機材、備品について、一般学生による予約申請と、管理担当者による予約・貸出・返却状態の管理を一つのWebシステムで行う。

現在は紙、口頭、表計算ファイルなどで個別に管理されており、情報の不一致、予約の重複、確認漏れ、貸出状況をすぐ確認できない問題がある。本提案では、特に情報を一元的に扱い、予約重複と状態の確認漏れを抑えることを重視する。

開発・利用上の主な制約は次のとおりである。

- 開発環境：XAMPP、PHP、MySQL/MariaDB、HTML、CSS、JavaScript、Git、GitHub
- 開発ツール：VSCode
- 動作環境：PC版ChromeまたはEdge
- 利用範囲：授業内で動作確認する学内向けWebシステム。一般公開は想定しない
- データ：実在する学生の個人情報を使わず、架空のテストデータを使用する
- 開発期間：前半セット第1回から第7回までに設計、開発、テスト、発表を行う
- 対象外：決済、メール送信、QRコード、外部カレンダー連携、リアルタイム通知

## 2. 利用者と解決する課題

### 想定利用者

| 利用者 | 要望書に記載された利用目的 | 現時点の扱い |
|---|---|---|
| 一般学生 | 施設・備品を探し、予約を申請し、自分の予約状況を確認する | 予約の申請者 |
| 管理担当者 | 施設・備品、申請、貸出、返却を管理する | 暫定的な最重要利用者 |
| 教員 | 学生と同様に予約する場合と、管理を補助する場合がある | 権限は未確定 |

チーム内では、管理担当者を最重要利用者とする意見が2名、一般学生を最重要利用者とする意見が1名であった。このため、現時点では**管理担当者を最重要利用者とする**。ただし、一般学生が利用人数・利用頻度の面で主利用者かどうかは要望書に記載がないため、依頼者への確認が必要である。

### 最優先で解決する課題

要望書「1.2 現在困っていること」のNo.2を最優先課題とする。

> 紙と表計算ファイルの情報が一致しないことがあり、予約の重複や確認漏れが発生する。

あわせて、No.3の「誰が何を借りているか、すぐに確認できない」という問題にも対応する。予約と貸出の情報を同一システムで扱い、対象物の状態を明確にすることで、管理担当者が現在の状況を確認しやすくする。

## 3. WISH別の優先順位と判断理由

| WISH | 要望の要約 | チームの優先順位 | 判断理由 |
|---|---|---|---|
| WISH-01 | 利用者のログイン | 必ず実装 | 本人の予約と管理機能を区別する入口であり、権限管理の前提になるため |
| WISH-02 | 学生と管理担当者の操作分離 | 必ず実装 | 学生による管理情報の変更を防ぎ、権限のない操作を制限するため |
| WISH-03 | 施設・備品の一覧 | 余裕があれば実装 | 学生が対象を探すために必要だが、チームは整合性を保つコア機能を先に実装すると判断したため |
| WISH-04 | 名前・分類による検索 | 余裕があれば実装 | 登録数増加時の利便性を高めるが、一覧や予約・状態管理より後に実装可能と判断したため |
| WISH-05 | 利用日を指定した予約申請 | 必ず実装 | 予約を記録として残し、紙や口頭による確認漏れを減らす中心機能であるため |
| WISH-06 | 管理担当者による承認・却下 | 余裕があれば実装 | 依頼者の希望には合うが、MVPでは重複がなければ予約を成立させる案でコア動作を先に完成させるため |
| WISH-07 | 貸出中・返却済み等の状態管理 | 必ず実装 | 誰が何を借りているかを確認可能にし、貸出・返却の確認漏れを減らすため |
| WISH-08 | 学生による自分の予約状況確認 | 余裕があれば実装 | 問い合わせ削減に有効だが、チームは申請・重複防止・状態管理を先に完成させると判断したため |
| WISH-09 | 予約の重複防止 | 必ず実装 | 最優先課題である予約重複に直接対応するため |
| WISH-10 | 利用回数・未返却の確認 | 今回は対象外 | 要望書上の優先度が「希望」であり、集計を前半セットに含めるか未決定であるため |

### 優先順位に関する注意

要望書ではWISH-03、WISH-04、WISH-06、WISH-08も「必須」とされており、WISH-03、WISH-06、WISH-08に対応する内容は完成時の確認事項にも含まれている。したがって、これらを「余裕があれば実装」とするチーム案は依頼者との合意が必要である。

## 4. 第7回までのMVP候補

### CAND-01 利用者認証（WISH-01）

- 一般学生と管理担当者がログインできる。
- 本人の予約だけを扱えるようにするための認証基盤とする。
- パスワードの扱い、不正な入力、未入力時の案内に配慮する。

### CAND-02 権限による操作制御（WISH-02）

- 一般学生と管理担当者で利用できる操作を分ける。
- 権限のない利用者が管理機能を操作できないようにする。
- 教員を独立した権限にするかは未確定とする。

### CAND-05 予約申請（WISH-05）

- 一般学生が対象と利用日を指定して予約を申請できる。
- 予約単位は、MVPでは日単位とするチーム案を採用する。
- 目的を必須にするか、キャンセルを可能にするかは未確定とする。

### CAND-07 貸出・返却状態の管理（WISH-07）

- 管理担当者が、少なくとも貸出中と返却済みを区別して管理できる。
- 申請中、承認済みを含む状態遷移は承認方式とあわせて確定する。
- 予約と貸出・返却を同一データとして扱うかは設計前に確認する。

### CAND-09 日単位の重複予約防止（WISH-09）

- 同一対象について、予約期間が重なる申請を検知する。
- 重複を検知した場合は登録を拒否し、利用者が修正方法を理解できるメッセージを表示する。
- 「重複を完全にゼロにする」ことは確約せず、判定範囲と例外を依頼者と合意する。

### MVPの成立に関するリスク

WISH-03を実装しない場合でも、予約対象を選択する最低限の手段は必要である。また、WISH-08を実装しない場合、学生が予約の成立を確認する手段が不足する。WISH-06を実装しない場合は、自動成立を依頼者が許容する必要がある。このため、一覧、申請結果表示、管理側の予約確認について、各WISHの全機能ではなくても一連の操作を成立させる最低限の画面を検討する。

## 5. 今回の対象外候補

### CAND-10 利用回数・未返却の集計（WISH-10）

WISH-10は今回の対象外候補とする。要望書で「希望」とされており、利用履歴の集計は将来的な活用として記載されているためである。

ただし、WISH-07の状態管理に必要な個別の貸出中・返却済み情報はMVPに含める。「未返却の集計・一覧」と「個別予約の状態管理」は分けて扱う。

要望書で明示された次の機能も今回の対象外とする。

- 決済
- メール送信
- QRコード
- 外部カレンダー連携
- リアルタイム通知

- 施設・備品の登録・変更をMVPに含めるか
- WISH-03、WISH-04、WISH-06、WISH-08を「余裕があれば実装」とする優先順位を許容できるか
- 予約の「目的」を必須入力にするか
- 初期データとして必要な利用者、分類、施設・備品の範囲

## 7. チーム独自の追加提案1件

### 検討案：予約内容の確認画面

予約を確定する前に、対象、利用日、返却予定日を学生が再確認できる画面を設ける案を検討した。誤った対象や日付での申請を減らし、「利用者が迷わず使えること」に寄与する可能性がある。

ただし、チームは**依頼者の既存要望を差し置いて追加機能を優先しない**と判断した。このためMVPには採用せず、WISHの実装後に余力がある場合の将来検討案とする。

## 9. 現時点の仮説・前提条件

以下は要望書で確定していないため、依頼者との合意前は確定要件として扱わない。

1. 管理担当者を最重要利用者とする。
2. 管理側が使いやすいシステムは、一般学生にとっても使いやすくなる。
3. 予約単位を日単位とし、同一対象は同じ日に1件だけ成立させる。
4. WISH-06を実装しないMVPでは、重複がなければ予約を自動成立させる。
5. 紙と表計算ファイルからWebシステムへ情報を一元化する。ただし、既存運用を完全に廃止するかは未確認である。
6. PHPとMySQL/MariaDBによる認証、権限判定、日付重複判定を中心に実装すれば、第7回までにMVPを完成できる。
7. データ構造、テーブル数、MVC等のアーキテクチャは未決定である。
8. WISH-03、WISH-04、WISH-06、WISH-08を後順位としても、最低限の予約・管理フローは成立させられる。
9. 追加提案は既存WISHを実装した後に検討し、MVPの要望を置き換えない。
